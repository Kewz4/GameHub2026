# Secure-channel synthetic QA fixture

This directory is isolated fixture evidence. It is not linked into the launcher,
does not enable a production overlay/input flag, and is not evidence that any
real game is compatible with the overlay.

The fixture closes one narrow design question: a reader may consume a
shared-memory readiness/release record without trusting a fixed, forgeable map.
It demonstrates the following Windows x64 contract:

- The coordinator creates a 256-bit CNG-random `Local` object namespace. Every
  named mapping/update event is created with a protected DACL granting access
  only to the current user, and creation fails closed on
  `ERROR_ALREADY_EXISTS`. Before generating any secret, the coordinator applies
  a protected DACL to itself; coordinator and reader process/thread DACLs expose
  synchronization and limited-query rights, not VM-read or handle-duplication
  rights.
- A 256-bit HMAC key and 256-bit session nonce are generated by
  `BCryptGenRandom`. They are never written to disk or placed on the command
  line. The key is delivered once through an anonymous pipe inherited through
  `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`.
- The pipe read handle, an unnamed ACK event, and a synchronization/limited-query
  handle to the coordinator process are the only fixture handles on the
  inheritance allowlist. The write end and 128 deliberately inheritable decoy
  handles are excluded; the reader proves all allowlisted handles work and the
  high-valued decoy is invalid. No ACK name exists for another map writer to
  infer or signal.
- Fixed-size key-bearing buffers are `VirtualLock`ed, bounded, and erased with
  `SecureZeroMemory` before unlock/normal exit. Abrupt-exit tests erase the
  coordinator copy immediately before termination; CNG hash handles are
  destroyed before their object buffers are erased; process teardown discards
  the remaining address space.
- Every HMAC-SHA-256 publication uses explicit fixed-width little-endian field
  serialization. It binds the nonce; exact reader and coordinator PID/creation
  `FILETIME`; executable `FILE_ID_INFO` volume/file ID; digest of each canonical
  handle path; generation; topology epoch; monotonic commit; state; flags; and
  slot bitmaps. Raw C++ structure padding is never authenticated.
- The mapped `SharedRecord` layout remains an isolated same-build Windows x64
  fixture ABI. The canonical authentication encoding is explicit, but this is
  not a cross-compiler or production wire-format claim.
- Readiness requires exact equality:
  `readySlotBitmap == requiredSlotBitmap == 0x7`. Extra or partial slots fail.
- Publication acquires an aligned even sequence with compare/exchange and owns
  the following odd value before writing. Readers accept only a stable equal
  even sequence and a valid HMAC. The hostile two-writer case requires measured
  CAS contention and a race-tagged heartbeat accepted while the hostile writer
  is active.
- Once a valid block is latched, malformed, forged, stale, torn, replayed, and
  incomplete release records cannot clear it. A matching authenticated release
  clears it. Signaling of the inherited synchronization-only coordinator process
  handle is an explicit owner-death fail-open path.
- Reader processes are assigned at creation to a kill-on-close Job Object for
  ordinary, timeout, and crash paths. The owner-death case intentionally omits
  that job so the orphan can prove the inherited coordinator process handle was
  signaled and release fail-open.

## Threat boundary

This fixture **does not claim security against a hostile process running as the
same Windows user**. The current-user DACL limits accidental cross-account and
direct-access exposure, while HMAC/identity/replay checks reject stale,
accidental, and map-only unauthenticated writers. They are not a same-user
security boundary.

The attacker probe deliberately records the reason. It validates the exact
coordinator PID and creation time, proves direct `PROCESS_VM_READ`,
`PROCESS_DUP_HANDLE`, and privileged-handle duplication fail after DACL
restriction, then proves that the same owner can still obtain `WRITE_DAC` and
successfully reapply the DACL. Such a process could re-ACL the coordinator and
escalate access; it is explicitly out of scope. The probe also derives the old
`-ack` name and proves no such named event exists.

## Acceptance matrix

`test.cjs` covers normal publish/release; pre-created map, update-event, and
wrong-object-type rejection; unknown-key and inferred-ACK spoof attempts; the
same-owner DACL limitation probe; wrong nonce; independently stale PID and
reader/coordinator creation time; wrong volume serial, file ID, and
canonical-path digest; stale generation and topology; odd/torn publication;
authenticated replay; extra-slot release; observed writer/reader heartbeats; a
hostile two-writer CAS race; owner death; job-contained timeout and coordinator
crash; and 24 parallel process pairs. The native sources compile as x64 with
`/W4 /WX`, SDL checks, CFG, ASLR, NX, and the static runtime.

Run the clean build and acceptance suite on Windows:

```powershell
node native/overlay-fixtures/secure-channel/build-and-test.cjs
```

The build script validates its exact disposable target path before deleting it,
recreates a fresh output tree, verifies x64/ASLR/NX/CFG headers, and then runs
the process-level matrix.

## Win32 contracts exercised

- `BCryptGenRandom` and CNG HMAC-SHA-256
- `CreatePipe`, handle inheritance flags, and Microsoft's documented
  [`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`](https://learn.microsoft.com/en-us/windows/desktop/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)
  contract
- [`CreateFileMapping`](https://learn.microsoft.com/en-us/windows/win32/memory/creating-a-file-mapping-object),
  `CreateEvent`, protected security descriptors, and `ERROR_ALREADY_EXISTS`
- `GetProcessTimes`, `GetFinalPathNameByHandle`, and `FileIdInfo`
- `InterlockedCompareExchange64` CAS publication and `MemoryBarrier`
- restricted
  [process access rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights)
  plus the documented
  [signaled process-object lifetime](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process)
- `PROC_THREAD_ATTRIBUTE_JOB_LIST` with the documented
  [`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)
  behavior

No upstream source code is copied into this fixture.
